# Native music finishing — v0.7.1

**September 15 rerun fix:** manually deleting Amplify from selected music now rebuilds the missing effect without dropping the rest of the pass record. Mixed selections replace surviving owned effects instead of stacking them. Partial updates retain records for unselected clips. Reload the plugin; no service restart required.

Updated September 15, 2026. **4. Conform & duck music** measures existing timeline music and writes editable native Amplify keyframes in the active sequence. The entire music pass runs locally inside the plugin, without Connect, a pairing token or the service. It never replaces or imports music media. Analysis is CPU-only and loads no models.

## Workflow

1. Reload the plugin. The service can remain stopped. Open the sequence containing your existing music and dialogue; select only the music clips to process.
2. Open **Options → Ducking**. **Duck against → Clean dialogue** remains the default and follows inserted WTV clean media in a finished/resumed cleanup clone. For an ordinary sequence, choose **Choose tracks** and check the dialogue tracks. Keep reference dialogue enabled, unmuted and unselected. The choice is saved per sequence; use **Refresh** after changing tracks.
3. Set the music target (default −20 dBFS), **Peak** (default) or **RMS**, reduction (10 dB), attack (200 ms), release (1200 ms) and Speech floor (−40 dBFS). Run step 4 and keep the timeline unchanged until completion.
4. Audition the result. Amplify gain keyframes are editable in Effect Controls. Source files, trims and placement remain intact. **Remove clip Volume before ducking** is on by default and removes Volume keyframes/fades; turn it off to retain them. Other effects remain.

Dialogue cleanup is optional for this workflow and still requires the service. If using it, complete steps 1–3 first, then select music in the finished clone. A pending or failed cleanup context must be finished or inspected before ducking that sequence.

Full sequence cleanup requires dialogue-only input; selected-dialogue filtering applies only to Per clip mode. Music as stem extracts a new file from cleanup input and is separate from this native music pass.

## Analysis and gain

One isolated scratch sequence exports a full-length temporary WAV of the **dialogue reference** only. The plugin reads it locally in bounded chunks and keeps 20 ms level summaries; nothing is uploaded. Duck keyframes are **relative** (0 dB baseline, subtract Duck dB while dialogue is present). Music level between lines is whatever you set on the timeline; this pass does not measure, compress, or normalize the bed.

Completed scratch sequences and temporary files are deleted. Interrupted exports may be retained when Premiere may still be writing.

## Performance and necessity (2026-09-15)

| Step | Required? | Typical cost on long timelines |
|------|-----------|--------------------------------|
| One full-sequence dialogue reference export | **Yes** — duck timing from rendered dialogue | **Dominant** (~1× sequence duration) |
| Local WAV read → 20 ms summaries | **Yes** | Medium |
| Offline `analyze()` CPU (relative duck envelope) | **Yes** | Usually seconds |
| Scoped timeline guards + effect snapshots | **Yes** (safety) | Reduced vs full-sequence video scan; still scales with reference clip count |
| Per-clip Amplify + keyframes + readback verify | **Yes** at scale | Scales with music clip count; batches ≤500 keys/transaction when safe |
| Optional strip clip Volume | User choice | One extra transaction when enabled |

Copy report **`Music timing:`** and **`Music render breakdown:`** lines record measured seconds after each run. Partial music selection still exports the **full sequence length** — only lanes are isolated, not shortened.

**Not removed:** triple export, calibration render, verify readback, pending ownership marker. **Follow-up:** optional cached analysis summaries on unchanged reruns (design only).

Activity comes from the selected dialogue reference: inserted Clean dialogue media by default, or all enabled, unmuted clips on explicitly chosen tracks, using the Speech floor setting (default −40 dBFS RMS), 200 ms hold, look-ahead attack and configurable release. It follows those lanes across gaps and overlaps. This is WTV's energy detector, not Adobe Essential Sound's algorithm. Residual noise above the threshold can keep music ducked. The current pass reports dialogue activity and the percentage of audible music ducked. Nearly continuous ducking generates a warning; zero detected dialogue stops the panel before music Apply when Duck is greater than zero. Use Duck = 0 for deliberate level-only conforming. Copy report retains the analysis summary even when the no-dialogue guard stops Apply.

The baseline gain is stored separately in the analysis plan and combined with the duck envelope in one additional Amplify effect per music clip. Rerunning with new settings replaces only the WTV-owned effect, avoiding doubled gain. Source-relative keyframe times account for in-points and timeline placement. As of September 15, curves retain only analysis corners and clip endpoints. Amplify’s normalized slider value is affine in dB, so native LINEAR interpolation represents those ramps directly; 0.25 dB subdivisions were redundant. A two-endpoint calibration ramp checks native behavior before Apply. The 8000-corner budget is checked before final Amplify insertion. Copy report includes actual native key counts and estimated counts under the old densification method.

Before timeline music is edited, the calibration render must reproduce a −3 to −9 dB ramp: median error at most 0.3 dB and 95th-percentile error at most 0.8 dB. This tests rendering as well as gain encoding and timing. Final installed keyframe values and interpolation are read back. Failed verification attempts to restore the previous effects; uncertain transactions remain marked for inspection rather than stacking another pass.

Selected music layout, trims, effect values, keyframes and interpolation are fingerprinted. Reruns require the same music clips (same track/index/source and source in/out points); moving a clip's position on the track alone is detected and reapplied at the new position automatically (see the 2026-09-10 follow-up). Retrimming a clip, changing its effects, or a different selection still requires a fresh cleanup clone. Manual edits or Undo can require a fresh cleanup clone. Ownership records live in panel storage, not a portable project format. Completed scratch sequences are removed before the final music transaction so the successful music edit is the latest undoable transaction.

## Limits and acceptance

Use neutral track/master processing, unity master gain and no track solos. Supports English Amplify, mono/stereo, sequences of at least 0.4 seconds, up to 100 selected normal-speed forward music clips, and at most 8,000 curve points per gain parameter (analysis simplifies to at most 6,000 global corners). Music transitions on selected clips are supported automatically (no manual removal needed), same as existing clip-volume fades. RMS or Peak baseline measurement; LUFS is out of scope for now. Required baseline gain must be −60 to +18 dB. The local predicted music sample peak is a conservative upper bound using each 20 ms block peak and maximum gain in that block; it may reject an RMS target near the ceiling more conservatively than the old sample-by-sample calculation. A bound above −0.1 dBFS stops the pass; this is not a true-peak limiter or certification of final combined dialogue/music loudness.

### Historical implementation notes

The following records describe earlier service-backed versions. Current plugin ducking uses `plugin/music-analysis.js`; `service/music.py` and its endpoint remain only for older/API clients. Reloading the plugin is sufficient for the offline update. Native offline acceptance is still pending.

### 2026-09-14: Peak baseline target mode, and LUFS removed

Added `target_mode: 'rms' | 'peak'` to `MusicAnalysis` in `service/music.py` (default changed to `'peak'` on 2026-09-14; was `'rms'` at introduction). In `'peak'` mode, the baseline gain targets the selected music's sample peak instead of active-audio RMS, so the resulting baseline (and therefore the ducked level, baseline − Duck dB) lands at a predictable sample peak. This was added because the default RMS target was reported as producing sample peaks roughly 10 dB above the entered number, which is expected for typical program material (RMS sits below peak by its crest factor) but was not what was wanted. Exposed in the panel as **Target counts as: RMS (active audio) / Peak** next to Music baseline in the Ducking **⚙** menu (`plugin/index.html`, `plugin/main.js`); the choice is a panel-only preference, persisted separately from job settings, and is sent as `target_mode` in the `/v1/music-analysis` request.

Separately, the global **Measure** RMS/LUFS toggle (Options → Levels & stems) was removed as out of scope: `unit` is gone from `service/schema.py`'s `Settings`, `service/audio.py`'s stem-target normalization is RMS-only now, and the corresponding UI/select/validation was removed from the panel. This is unrelated to the music-pass `target_mode` above — the ducking pass never supported LUFS and already rejected it explicitly before this change.

### 2026-09-14: music transitions no longer rejected

Previously, selecting a music clip with any transition on its track threw `Music transitions need a separate host validation pass. Use clip-volume fades for this preview.`, requiring the user to manually convert crossfades to clip-volume fades before ducking. Removed: every render this pass performs already isolates the selected/reference clips by disabling every other clip, and a disabled sibling contributes silence across a transition boundary -- exactly the right substitute for isolating this clip's own audible envelope, fade shape included. The duck automation is a per-clip Amplify effect, which composes with an adjacent transition exactly like any per-clip effect always does in Premiere (effects apply before a transition mixes its two sides), so nothing about a transition being present changes that composition. The calibration render's own tight verification (median/95th-percentile error against a known deterministic ramp) remains in place as a safety net that would catch and fail loudly on any unexpected transition-rendering behavior, rather than this silently producing wrong keyframes. **Not yet confirmed against real Premiere** -- reasoned from confirmed behavior elsewhere in this codebase (per-clip effect/transition composition, disabled-clip isolation), not from a live test of this exact combination.

Automated tests cover DSP, dialogue activity, time mapping, gain conversion, effect preservation, reruns, rollback, source changes, selection filtering, service authorization and temporary asset cleanup. Real Premiere execution is still an acceptance check on the user's host. Mocked tests do not establish native effect compatibility with that build. The button's runtime calibration checks it before editing the music; use Copy report if it fails. No new GPU inference was run for this feature.

## Review on 2026-09-09

The user first reported that ducking may not work correctly (music stays unchanged, no WTV Amplify effect visible in Effect Controls). An initial API/timing review found no confirmed mismatch. The user then supplied the exact live Premiere runtime error: `component.getParamCount is not a function`, which pinpointed the real defect.

**Root cause and fix.** `AudioFilterFactory.createComponentByDisplayName()` returns a bare `AudioFilterComponent` handle. Per Adobe's UXP type declarations this type has no methods at all; `getParamCount()`/`getParam()` exist only on the `Component` type returned by `AudioComponentChain.getComponentAtIndex()`, i.e. only once a component has actually been appended into the chain via a committed transaction. `plugin/music-effects.js`'s `prepare()` called `component.getParamCount()` on the raw factory handle before any append happened, throwing immediately and aborting the pass before the Amplify effect was ever added — explaining both the error and "no effect present at all". The module's own `verify()` already re-fetched an installed component from the chain the correct way; `prepare()` just never did that first.

Fixed by splitting the flow into `createComponent()` (factory call only), `installed()` (re-fetch the real `Component` from the chain after the append transaction commits) and `configure()` (read params / build keyframes on that installed object). `plugin/music-pass.js`'s calibration probe and final Apply now each run two transactions — append the effect, then commit its keyframes — instead of one. `tests/music-pass.test.cjs`'s mocks previously gave the factory-created handle full parameter methods immediately, an idealized shape that could not have caught this; they now model the same handle/installed split, plus an explicit regression test. Full suite: 79 Python / 61 JS passing. **Still outstanding: confirmation against real Premiere.**

Separately, an inspection of recent local clean-dialogue outputs found one 15.18-second clip above −40 dBFS in 97.37% of its 20 ms frames. This establishes that the current energy detector would remain active through most of that clip; it does not label the sound as noise or prove that this is the user's failing timeline. Added the adjustable speech floor and reporting described above, plus no-dialogue protection and regression tests. No VAD model, Adobe Essential Sound trigger, or speculative keyframe-time conversion was substituted.

## Follow-up on 2026-09-09: "Unrecognized Amplify gain representation."

Rerunning after the fix above got past parameter identification and immediately hit the next guard: `configure()` reads the `Left`/`Right` parameter's current value as `base` and requires it to be a plain JS `number`, throwing this generic message otherwise. Adobe's own [`ComponentParam.getValueAtTime()`](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/componentparam) reference documents its return type as `number | string | boolean | PointF | Color` depending on the parameter's underlying type — i.e. Premiere itself, not just this plugin's guess, can legitimately hand back a numeric value as a `string`. The strict `typeof base!=='number'` check rejected that outright instead of reading it.

Fixed by coercing a numeric string (e.g. `"0"`) to a real number before validating, in `music-effects.js`'s `configure()`. If the value is still not usable after that — a boolean, `PointF`, `Color`, or a non-numeric string, none of which make sense for a gain control — the error message now also reports the raw value and its `typeof` (`Unrecognized Amplify gain representation for "Left": ... (typeof ...)`), so if this specific guard ever fires again in real Premiere, the report will show exactly what Left/Right actually returned instead of leaving it another blind guess. Two regression tests added: one confirming a numeric-string base is coerced and produces the expected encoded keyframe value, one confirming a genuinely unusable value (a boolean, standing in for `PointF`/`Color`) still throws with the new diagnostic detail. Full suite: 68 JS passing. **Still outstanding: confirmation against real Premiere** — if this specific representation guess is also wrong, the improved error text is designed to make the *next* fix a one-shot instead of more back-and-forth.

## Follow-up on 2026-09-09: "...Found: {"value":0.6666666865348816} (typeof object)."

The diagnostic detail added above paid off immediately: `Left`'s base value is neither a plain number nor a numeric string, but a **boxed `{value: <number>}` object** — a marshalling shape absent from Adobe's own documented `number | string | boolean | PointF | Color` union for `getValueAtTime()`. This matches a pattern other UXP developers have already hit on other native parameter types (e.g. the community-reported "Color parameter writes lose the blue channel" and "Source Text value does not survive the crossing" issues) — Premiere's own value marshalling for some parameter shapes is inconsistent with its documentation, not something guessable from spec alone.

Fixed the same way as the string case: `configure()` now also unwraps `base.value` when `base` is an object with a finite numeric `value` field, before validating. Added a regression test using the exact reported value (`0.6666666865348816`) to lock this in. Full suite: 69 JS passing.

**Important note on what happens next, regardless of whether this guess is also wrong:** the existing calibration step (see "Limits and acceptance" above) renders a real −3 to −9 dB probe ramp through the actual installed effect and measures the resulting audio, rejecting the pass if median error exceeds 0.3 dB or 95th-percentile error exceeds 0.8 dB. That check is independent of whatever `base` turns out to mean — if `0.6666666865348816` is not actually a linear amplitude ratio (unlikely given the value, but not proven), the pass will fail there with **"Music gain calibration did not pass"** rather than silently applying wrong-sounding ducking, and Copy report will carry the measured error. That would be a materially different, more informative failure than this one, worth reporting back precisely if it happens.

## Follow-up on 2026-09-09: "Premiere music keyframe readback failed."

The next run got past calibration and the write phase, then failed in `verify()` — a *different* function from `configure()`, with its own separate `getValueAtTime()` call that never received the string/boxed-object coercion fixed above. If Premiere returns the same `{value: <number>}` shape when reading back an already-written keyframe (not just the initial pre-keyframe base value), the old strict `typeof read!=='number'` check would reject it and throw this generic message even though the write had actually succeeded.

Refactored the coercion into a shared `coerceGainValue()` helper in `music-effects.js`, used by both `configure()` (reading the base) and `verify()` (reading back each keyframe) so this class of quirk can't reappear unfixed in one call site while patched in the other. Also split the single generic "readback failed" message into three specific ones, since there are three genuinely different failure modes that were previously indistinguishable:
1. **The keyframe position is entirely missing** from Premiere's own keyframe list — this is a different, more serious failure than a value mismatch. It matches a [confirmed-but-unresolved Adobe UXP bug](https://community.adobe.com/questions-729/unable-to-set-mutliple-keyframes-with-uxp-1548880) where `createAddKeyframeAction()` can silently drop all but the last keyframe for some track item types. (That thread's specific root cause — keyframe time not offset by the clip's source in-point — does **not** apply here: `clipCurve()` already adds `clip.inPoint`, confirmed by the existing test asserting `keys[0].position.seconds === 30` for a clip with `inPoint=30`. But it establishes that Premiere/UXP's keyframe-add path has real, Adobe-acknowledged failure modes independent of this plugin's code, so this specific message is written to be identifiable as *that* class of problem if it recurs.)
2. **The keyframe exists, but its value doesn't match** what was written (now after coercion) — the value-marshalling quirk, same family as the base-value bug.
3. **The keyframe exists with the right value, but wrong interpolation mode.**

Each now reports the exact time, parameter name, and (for a value mismatch) the raw returned value and its type. Two new regression tests added: one confirming `verify()` now accepts a boxed-object readback instead of false-flagging it, one confirming a genuinely missing keyframe reports its specific position/parameter. Full suite: 71 JS passing. **Still outstanding: confirmation against real Premiere** — if this fires again, the specific one of the three messages above will say which of these distinct failure modes actually happened, which is now real information rather than another blind guess.

## Follow-up on 2026-09-09: root cause found — "median error 42.41 dB, 95th-percentile error 54.26 dB"

The diagnostic added above immediately delivered a decisive number: 42-54 dB is not a rounding error, it's roughly two orders of magnitude off, ruling out the "small systematic offset" branch above. The suspiciously exact `base = 0.6666666865348816` (`2/3` to 8 significant figures) was the clue: that's what you get if `Left`/`Right` is a **normalized `[0,1]` slider position on a fixed, wide, linear-in-dB range** rather than a linear amplitude ratio — e.g. on a 144 dB-wide range, `0 dB` (a fresh Amplify's default) normalizes to exactly `96/144 = 0.6667`. Modeling the error this way (fitting the wrong multiplicative-ratio formula against a hypothetical 144 dB-wide additive-normalized range) predicted errors ramping from ~25 dB to ~53 dB across the -3→-9 dB probe — closely matching the real 42.41/54.26.

Rather than guess the exact range a 7th time, the user checked Premiere's own Effect Controls UI directly for the Amplify effect: **Left/Right display in dB, default `0 dB`, range `-96 dB` to `+48 dB`** (a 144 dB span — confirming the hypothesis exactly: `(0-(-96))/144 = 0.66666...`, matching the live `base` value to 10 significant figures). This is not a linear amplitude ratio at all; it is that dB value's normalized position on this fixed range.

Fixed in `music-effects.js` by replacing the entire `base * 10^(db/20)` ratio formula with the confirmed absolute mapping `dbToNormalized(db) = (db - (-96)) / 144`, which no longer depends on reading `base` to compute keyframe values at all (the previous design multiplied relative to whatever the live default happened to be; the real mapping turned out to be a fixed absolute scale, not relative to a read value). Two safety checks were added since this is now the third fundamentally different encoding formula tried on this same live measurement: (1) every dB value in the requested curve is checked against the confirmed -96..+48 dB bounds before writing, since a value outside that range would normalize outside `[0,1]` and risk silent clamping — the same *symptom* as this bug, from a different cause; (2) the live default is still read and compared against the confirmed 0 dB point (within 0.01 normalized units) as a sanity check, throwing a specific, actionable error (`Amplify "Left" default is X dB, not the expected 0 dB`) if some other Premiere build/locale's Amplify doesn't match this exact range, rather than silently miscalibrating a fourth time.

`base` is no longer used to compute the encoding itself, only for that sanity check, so the `coerceGainValue()` string/boxed-object handling built up over the last several fixes is now purely defensive (still needed for reading that sanity-check value, and for `verify()`'s readback) rather than being on the hot path of every keyframe's value. Test suite updated throughout `tests/music-pass.test.cjs`: the default mock base changed from `0` to `2/3` (0 dB) to satisfy the new sanity check; the old "amplitude-valued gain parameters" test (which asserted the now-disproven `10**(db/20)` ratio result) was replaced with three focused tests — correct encoding onto the confirmed range, the sanity check rejecting an off-default component, and `verify()`'s readback-mismatch check kept independent of units. Full suite: 73 JS passing.

**Still outstanding: confirmation against real Premiere.** This is the first fix in this whole chain backed by a live, human-read ground-truth value (the Effect Controls UI's displayed range) rather than an inferred guess, so confidence is meaningfully higher than the previous six rounds — but the actual audible result in real Premiere has not yet been confirmed.

## Follow-up on 2026-09-09: reverted `project.lockedAccess()` after a fatal Premiere crash

The very next real run after the dB-encoding fix above **crashed Premiere Pro entirely** (not a caught JS error). Confirmed via Sentry's own crash breadcrumb (`SentryIO-db/reports/*.dmp` + its sibling `__sentry-event`/`__sentry-breadcrumb1` attachments): a fatal fault inside Adobe's own native scripting bridge, `AsyncScriptTaskQueue.cpp`'s `ProcessPromise`, while resolving a `Promise<boolean>` in this plugin's script context (`com.wtv.audiowizard`) — with `message: "Crashed with context"`.

The prime suspect: the `project.lockedAccess(() => {...})` wrapping added around `configure()`'s `createKeyframe()` loop in the "Action creation in locks" fix (see above). That change was speculative — motivated by Adobe's changelog, not by any observed staleness bug — and had never actually run against real Premiere before this crash. Calling a synchronous "lock" callback from deep inside an `async`/`await` chain is a plausible way to corrupt the native engine's own promise/microtask queue, and the crash's exact signature (promise resolution, boolean value, this plugin's context) lines up with that theory closely enough to act on. ## Follow-up on 2026-09-09: native ducking confirmed working, then a rerun-after-undo usability bug

With the dB-encoding fix and the `lockedAccess()` revert both in place, the user confirmed **native ducking works** in real Premiere — the first end-to-end success on this feature.

Immediately after, a follow-on usability bug surfaced: the user undid the pass with Ctrl+Z (which worked correctly — it cleanly removes exactly the Amplify effect the pass added), then moved the music clip and re-ran the music pass. Instead of running a fresh pass, it threw `Select the same unchanged music clips to update the previous pass. A changed timeline needs a fresh cleanup clone.`

**Root cause**: `run()` in `music-pass.js` persists an "ownership" record to the panel's own `storage` (not Premiere's undo stack, which UXP cannot observe) after each successful pass, recording each music clip's identity (`key`, encoding track/index/sourceId/timeline position/trim) and which effect index it owns. On the next run, it compares the *current* clips' keys against that stored record and throws this error on any mismatch — added specifically to stop a rerun from blindly reusing a stale effect-index reference if the timeline changed underneath it (see the `getParamCount`/parameter-identification fixes above, all of which stemmed from exactly this kind of stale-assumption bug). Moving the clip changes its key (timeline position is part of clip identity here), so the guard fired — but Ctrl+Z had *already* removed the very effect this guard exists to protect, so in this specific combination there was nothing left to protect, and the error was just noise blocking a legitimate rerun.

**Fix**: before comparing keys, a new `stillOwnsEffects()` check in `music-pass.js` asks a more direct question than "did anything about the clips change?" — namely, is the previously-recorded owned effect actually still sitting where the record says it is (same component index, same `getMatchName()`, read from the whole-chain snapshot `after` already stored at the end of a successful pass)? If it's gone from every music clip — consistent with a clean Ctrl+Z of exactly the "WTV: conform and duck..." transaction, which removes only what it added — the stale ownership record is discarded and the run proceeds as a fresh first pass, with no comparison against the old (now-meaningless) keys. If the recorded effect **is** still present, the original exact-key comparison still applies and still blocks a mismatched rerun — that's the genuinely risky case (the owned effect is still there; blind reuse of its index if something else changed could still touch the wrong effect), which this fix intentionally leaves alone.

Two regression tests added to `tests/music-pass.test.cjs`: one confirms a clean Ctrl+Z (effect removed) plus a clip move now succeeds as a fresh pass; the other confirms a clip move **without** the effect being removed is still blocked, so the real protection this guard exists for isn't weakened. Full suite: 75 JS passing.

## Follow-up on 2026-09-10: moving a music clip (without undoing first) now silently re-ducks at the new position

Dan asked for the workflow to be simpler than "Undo, move, rerun": moving the music clip and rerunning should just work, without needing to undo first. The previous fix above only handled the case where Ctrl+Z had *already* removed the owned effect; it still hard-blocked a plain move with the effect still present, requiring a fresh cleanup clone.

**Why a plain move can be handled safely at all**: Amplify's duck keyframes are written in clip/source-relative time (`music-effects.js`'s `clipCurve()`, anchored at `clip.inPoint`), not absolute sequence time — moving a clip along the track (without retrimming it) changes nothing about its own effect chain. Every rerun of step 4 already re-renders and re-analyzes the *current* timeline from scratch regardless, so the "same clips, new position" case was always going to get a correct fresh curve computed for it — the only thing actually stopping this before today was the exact-key comparison in `run()`, which folds timeline position into clip identity.

**Fix**: `music-pass.js`'s `describe()` now records two fingerprints per clip: the existing position-inclusive `key` (unchanged, still used for calibration-scratch bookkeeping within a single run), and a new `identity` — the same fields minus timeline position (`trackIndex`, `index`, `sourceId`, source in/out points). The previous-pass continuity check now requires matching `identity`, not matching `key`; if identities match but keys don't, that's exactly "the same clips, just moved" — reported via `say()` (`Selected music moved since the previous pass; recomputing ducking at the new position.`) and allowed to proceed as an ordinary rerun (remove the previously-owned effect, recompute the plan, add a fresh one), rather than blocked. A genuine retrim (different source in/out points) still changes `identity` too, and is still blocked exactly as before — that case can expose different underlying audio, which is a real enough change to still require a fresh clone. Two other lookups that previously matched by `key` (the scratch-sequence effect-removal step inside `render()`, and the restore-on-failure path) were updated to match by `identity` for the same reason — both need to find a moved clip's prior record too.

Replaced the test that had asserted a plain move was blocked with one asserting it now succeeds (re-ducks, swaps in a fresh effect, leaves the pre-existing fade untouched, and surfaces the "moved" notice), and added a new one confirming a genuine retrim is still blocked, so the two cases stay distinguishable going forward.
